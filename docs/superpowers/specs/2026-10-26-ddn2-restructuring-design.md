# DDN 2.0: four policy pillars with preserved domain history

Date: 26 October 2026. Status: approved by the user on 26 October 2026, including versioned routes and execution of all remaining phases.

Builder check: an independent software-engineering reviewer read this design and the impact assessment and returned "nothing important left". This confirms planning clarity, not implementation correctness or human approval.

## Intent

Restructure the stakeholder dashboard to the four client-approved Teras while preserving every existing domain capability, source meaning, historical record and permission boundary. This is a policy taxonomy change throughout navigation, analysis, workflows and reporting, not a replacement of underlying observations.

## Approaches

The user selected **versioned mapping**, retaining five stable data/access domains beneath four policy pillars. This requires explicit translation at presentation and navigation boundaries but avoids mutable-history and permission hazards.

A physical renumbering migration would require new versions of definitions, publications, report resources and grants and could cause privilege escalation. It is rejected for this change. Cosmetic renaming would lose harm functionality or misclassify international records and is inadequate.

## Model and storage

Introduce explicit types and helpers for `PolicyPillarId` (1–4) and `LegacyDomainId` (1–5), a mapping version identifier and exhaustive domain-to-pillar / pillar-to-domains lookups. Central metadata supplies titles and navigation. Avoid passing page numbers into existing authorization checks.

Retain existing database `teras` fields as legacy domain identifiers. Document this meaning in the DAL/contracts. Existing KPI codes (including D-T4-* and D-T5-*), definition versions, source catalogs, publication IDs, observation values, submission predecessors and access revisions remain unchanged. Do not renumber old migrations, reseed existing history or replace immutable records. No destructive database migration is needed.

New DTO presentation metadata can carry mapping version, current pillar and original domain. Existing API v1 `teras` fields retain their original semantics. If a new API accepts policy identifiers, use a separately named/versioned field plus explicit domain, validate membership and reject mismatches; do not silently reinterpret old integers. Default implementation should reuse v1 domain contracts through a typed adapter rather than add an unnecessary API version.

## Routes and compatibility — proposed implementation choice

Use `/ddn-2/teras/1` through `/ddn-2/teras/4` as canonical current pages. All navigation generated by the application points there. This makes the policy version explicit and preserves the meaning of every existing bookmark without guessing when it was created.

Legacy `/teras/1`, `/teras/2`, `/teras/3` redirect to their mapped pages; `/teras/4` redirects to `/ddn-2/teras/2?domain=harm`; `/teras/5` redirects to `/ddn-2/teras/4`. Preserve recognized filters, perspective, cohort and setting where applicable, validate all query values, and explain inapplicable geography on international views. International stays national-scope. Old action/registry query strings retain legacy semantics; new links explicitly identify the DDN 2.0 mapping and domain.

Alternative, if the human insists on retaining `/teras/4` for the new pillar: an explicit legacy-link resolver or disambiguation screen is required; unversioned old/new meanings cannot be distinguished automatically. That choice is not assumed.

## Merged Teras 2

Provide two clearly labelled, keyboard-accessible subviews within the one pillar: treatment/recovery and harm/public health. URL domain selection persists alongside common filters and the five evaluation perspectives. Both subviews retain their current needs, process, outcomes, cost and satisfaction capabilities.

Treatment keeps supplied caseload, facilities, mandatory/voluntary pathways, demographics, source settings, care funnel, cohort picker, follow-up loss, retention and reintegration. Harm keeps harm map/service-gap access, event/service distinction, screening cascade, intervention matrix, trends, support/barriers and existing conditional clinical definitions.

Default to treatment when authorized; a harm-only user lands on the permitted harm subview. A user without either grant sees an honest access/no-data state. A user with both can switch freely. Controls may identify domain names but must not leak unauthorized values, counts, metadata or scenarios. Each subview asks the DAL for its own authorized domain; permissions are not unioned into a broader grant.

Do not sum clients, screenings, events, contacts or service counts. Do not average incompatible rates or duplicate records in a combined total. The change does not establish new clinical outcomes, deduplication rules or agency data linkage.

## Other pages and responsibility

Teras 1 and 3 retain their present capabilities under their approved new titles. The title Ramalan Risiko does not enable forecasting, individual scoring or predictive policing. New Teras 4 retains the former international partner map, commitments, lifecycle, practice transfer and perspectives. Existing action/governance capabilities may be linked; no invented inclusive-governance score or diplomatic authority.

Update sidebar, overview, illustrations, AIDA local navigation, map handoffs, registry, catalogue, headings and administrative selectors. Long titles must wrap cleanly without hiding the full accessible name. Registry current-pillar filters include both treatment and harm definitions for Teras 2, subject to existing scope. Show source-domain provenance where needed to interpret stable codes.

Retain AADK, JPPP, JRP, JPU, JKMD and MTMD statements explicitly as sourced DDN 2017 relationships. JRP is not automatically the exclusive authority for the merged public-health domain. Harm and international responsibility remain distributed/validation-required; organization revisions remain effective-dated.

## Workflow, collaboration and reports

Uploads use four pillar groupings with an explicit domain/template choice where necessary. Keep all eight existing templates and their indicator/domain checks, quarantine, scanning, attest/review/publish permissions and independent approval. Display both current pillar and domain on history rows to prevent new Teras 4 being confused with historical harm domain 4. Revisions retain their predecessor domain.

Actions/notes remain attached to their original context and access scope. A combined Teras 2 action list is a deduplicated union of authorized domains, while creation selects a concrete domain and does not broadcast notes into both. Existing unversioned links keep their original meaning.

Frozen saved-report-v1 snapshots and old export resources remain interpretable and are not rewritten. New saved reports must record the mapping version alongside original definition/publication/access identifiers. Parsing must support historical snapshots without inventing a version. Any changed persisted shape gets an explicit compatible version strategy and tests. Export labels may show DDN 2.0 and source domain; download reauthorization continues against original resource scope. No new combined outcome totals. Reporting support remains bounded to existing capabilities; the restructuring does not imply every decorative chart already has an export API.

## Acceptance criteria

1. Exactly four current pillar navigation entries use the supplied titles; all canonical and legacy routes resolve correctly with validated analytical context.
2. Every existing treatment and harm perspective remains reachable within Teras 2. All other domain capabilities remain reachable in the mapped pages.
3. Treatment-only, harm-only, international-only, combined and no-access users see exactly their authorized resources. Server responses, RSC/HTML, metadata, action counts, upload endpoints and exports do not leak the other domain.
4. Source reconciliation totals/hashes, existing publication/definition IDs, immutable history, workflow predecessors and access grants are unchanged. No duplicate observations or artificial combined totals.
5. Both merged domains complete upload → validate → attest → independent approve → publish → view/export (where currently supported) → revise. Incorrect template/domain pairs and self-approval still fail.
6. Registry/catalogue map current pillars accurately; old requirement and indicator IDs remain traceable. Responsibility statements preserve source and qualification.
7. Historical report snapshots retain original meaning; new mapping metadata round-trips; permission revocation denies subsequent export/download.
8. Existing map layers and zero/missing/suppression semantics remain distinct. No forecast or policy threshold is invented.
9. Desktop/mobile/320px, light/dark, keyboard navigation, automated axe checks, all perspectives and long BM labels pass relevant checks. Manual screen-reader limitations are reported separately.
10. Formatting, lint, strict types, unit/contract, actual PostgreSQL/PostGIS, full E2E and production build pass; retained legacy references are classified rather than blindly deleted by a text search.
