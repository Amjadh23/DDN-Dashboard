# General Spec-Driven Development Workflow with ChatGPT + Codex

## 1. Purpose

This document explains a general workflow for using ChatGPT and Codex together in a controlled spec-driven development process.

It is meant to be reused across different projects and chats. It does not assume a notebook-based project. The same pattern can be used for software projects, data science projects, dashboards, automation scripts, research prototypes, or AI/ML systems.

The goal is simple:

```text
Do not ask Codex to “just build it.”
Create a clear project contract first.
Then let Codex implement under that contract.
```

This turns AI coding from a loose prompt-based workflow into a structured development process.

---

## 2. Core Idea

The workflow is:

```text
Human intent
→ ChatGPT turns intent into structured project instructions
→ Codex reads those instructions inside the repo
→ Codex implements the project step by step
→ tests/commands/outputs validate the implementation
→ human reviews and accepts or rejects
```

In short:

```text
ChatGPT designs the contract.
Codex builds from the contract.
Tests prove whether the build works.
Human makes the final decision.
```

---

## 3. Why This Workflow Is Needed

Codex is powerful because it can work inside a repository, read files, edit code, and run commands.

But without clear constraints, Codex may:

- build the wrong thing,
- skip important steps,
- over-engineer the solution,
- hide logic in unwanted places,
- modify files that should be protected,
- satisfy requirements superficially,
- generate code without validating it,
- or drift into features that were not requested.

Spec-driven development reduces this by giving Codex a project-level instruction system.

---

## 4. Role Separation

### 4.1 Human

The human owns the project.

The human decides:

- the goal,
- the scope,
- the constraints,
- what is acceptable,
- what is rejected,
- and when the project moves to the next phase.

The human should not rely only on Codex saying “done.” The human reviews the output against the spec.

---

### 4.2 ChatGPT

ChatGPT acts as:

```text
architect
spec writer
prompt engineer
review assistant
debugging partner
```

ChatGPT is used before Codex to create the project’s instruction files and prompts.

ChatGPT helps generate:

- project context,
- repo rules,
- requirements,
- plans,
- Codex prompts,
- validation criteria,
- and acceptance checklists.

ChatGPT is also used after Codex runs to review the report, diagnose failures, and refine the next prompt.

---

### 4.3 Codex

Codex acts as:

```text
repo implementer
code editor
command runner
test runner
artifact generator
```

Codex should work inside the repository and follow the files written by ChatGPT.

Codex should:

- read the instruction files,
- inspect the project,
- update the spec or plan if needed,
- implement bounded tasks,
- run validation,
- and report exactly what changed.

Codex should not be treated as an unrestricted autonomous developer.

---

A strong general SDD setup uses:


```text

```

For many projects, the lean setup is enough:

```text
AGENTS.md
PROJECT_CONTEXT.md

README.md
```

## 6. What Each File Does

### 6.1 `AGENTS.md`

Generated by: usually ChatGPT, then maintained by the human/Codex.

Purpose:

```text
Controls how Codex behaves in the repo.
```

It should define:

- required reading order,
- files Codex may edit,
- files Codex must not edit,
- coding standards,
- data/privacy rules,
- validation requirements,
- stop conditions,
- reporting format,
- and communication expectations.

Think of `AGENTS.md` as the repo-level constitution for Codex.

---

### 6.2 `PROJECT_CONTEXT.md`

Generated by: ChatGPT with human input.

Purpose:

```text
Explains what the project is and why it exists.
```

It should include:

- project title,
- project objective,
- current phase,
- background,
- target users,
- dataset or input assumptions,
- required outputs,
- allowed methods,
- prohibited methods,
- constraints,
- and definition of done.

This is the source of truth for project meaning.

---

### 6.3 `SPEC.md`

Generated by: Codex or ChatGPT, based on `PROJECT_CONTEXT.md`.

Purpose:

```text
Defines exactly what must be built.
```

It should include:

- functional requirements,
- non-functional requirements,
- input/output requirements,
- architecture requirements,
- validation requirements,
- edge cases,
- and acceptance criteria.

`SPEC.md` is the build contract.

If `PROJECT_CONTEXT.md` says what the project means, `SPEC.md` says what the system must do.

---

### 6.4 `PLANS.md`

Generated by: Codex or ChatGPT, based on `SPEC.md`.

Purpose:

```text
Defines how the work will be implemented.
```

It should include:

- milestones,
- task sequence,
- implementation order,
- commands to run,
- validation steps,
- progress log,
- blockers,
- and completion criteria.

`PLANS.md` prevents Codex from jumping straight to a giant uncontrolled implementation.

---

### 6.5 `README.md`

Generated by: ChatGPT or Codex.

Purpose:

```text
Explains the project to humans.
```

It should include:

- what the project does,
- setup instructions,
- how to run it,
- expected outputs,
- repo structure,
- dependencies,
- and limitations.

`README.md` is not primarily for controlling Codex, but Codex can use it for orientation.

---

### 6.6 `REFERENCES.md`

Generated by: ChatGPT or Codex when reference projects/files exist.

Purpose:

```text
Explains which previous projects or documents Codex may learn from.
```

It should state:

- what references exist,
- what Codex should extract from them,
- what Codex must not copy blindly,
- and what differences matter in the current project.

Use this when adapting a pattern from an older completed project.

---

### 6.7 `SKILL.md`

Generated by: ChatGPT when there is a reusable workflow.

Purpose:

```text
Stores reusable method rules for a class of projects.
```

Examples:

- healthcare ML workflow,
- dashboard build workflow,
- paper-writing workflow,
- data cleaning workflow,
- API integration workflow,
- deployment workflow.

`SKILL.md` should not replace `SPEC.md`.

The distinction is:

```text
PROJECT_CONTEXT.md = this project’s meaning
SPEC.md = this project’s requirements
PLANS.md = this project’s execution plan
SKILL.md = reusable technique or workflow
```

---

### 6.8 `TASKS.md`

Optional.

Purpose:

```text
Tracks granular task checkboxes.
```

This is useful for large projects, but often `PLANS.md` is enough.

---

## 7. File Generation Responsibilities

### 7.1 Files ChatGPT Usually Generates First

ChatGPT is best used to generate the initial SDD layer:

```text
AGENTS.md
PROJECT_CONTEXT.md
initial SPEC.md draft
initial PLANS.md draft
README.md draft
REFERENCES.md if needed
SKILL.md if reusable workflow is needed
```

ChatGPT is especially useful when the human has messy context and needs it turned into clean repo instructions.

---

### 7.2 Files Codex Usually Generates or Updates

Codex is best used to generate or update files based on actual repo inspection:

```text
SPEC.md updates
PLANS.md updates
source code
tests
configs
scripts
docs updates
output files
implementation reports
```

Codex should inspect the repository before finalizing implementation details.

---

### 7.3 Files the Human Controls

The human should approve or directly control:

```text
project scope
methodology decisions
sensitive data rules
final acceptance
major architectural changes
```

Codex can suggest changes, but the human decides.

## 8. Recommended Workflow Stages

## Stage 1 — Human explains the project to ChatGPT

The human gives ChatGPT:

- project goal,
- current repo situation,
- what is finished,
- what is missing,
- constraints,
- references,
- and desired outputs.

The goal is not to code yet. The goal is to create a strong instruction system.

---

## Stage 2 — ChatGPT creates the SDD files

ChatGPT drafts:

```text
AGENTS.md
PROJECT_CONTEXT.md
SPEC.md
PLANS.md
README.md
```

Optional:

```text
REFERENCES.md
SKILL.md
TASKS.md
```

These files should be specific enough that Codex cannot easily misinterpret the project.

---

## Stage 3 — Human places files into the repo

The human adds the generated markdown files to the repository.

If a file already exists, update it instead of duplicating instructions.

Avoid too many overlapping files. Conflicting instructions confuse Codex.

---

## Stage 4 — Codex performs repo inspection

First Codex prompt should usually be non-destructive.

Example:

```text
Read AGENTS.md first.

Do not edit code yet.

Inspect the repository and report:
1. current structure,
2. what files exist,
3. whether the SDD files are consistent,
4. what is missing,
5. what you recommend doing next.

Stop after the analysis.
```

This prevents Codex from rushing into implementation.

---

## Stage 5 — Codex updates SPEC and PLANS if needed

After repo inspection, Codex may update:

```text
SPEC.md
PLANS.md
```

This should happen before implementation if the repo reality differs from the original plan.

Codex should not silently change project scope. It should report any mismatch.

---

## Stage 6 — Codex implements one bounded milestone

Do not ask Codex to do everything at once unless the task is small.

Use prompts like:

```text
Implement Milestone 1 from PLANS.md only.

After editing:
- run the smallest relevant validation,
- report files changed,
- report commands run,
- report remaining TODOs,
- then stop.
```

This creates control points.

---

## Stage 7 — Codex validates

Validation must be objective.

Depending on project type, validation may include:

- unit tests,
- smoke tests,
- linting,
- type checks,
- script execution,
- API checks,
- output file checks,
- notebook execution,
- app build,
- or manual validation steps.

The definition of done should not be “the code exists.”

The definition of done should be:

```text
the project runs
the expected outputs are produced
the tests pass
the implementation matches the spec
```

---

## Stage 8 — Human reviews

The human checks:

- did Codex follow the instructions,
- did it modify forbidden files,
- did it implement the right thing,
- did it validate properly,
- did it hide logic somewhere unwanted,
- did it over-engineer,
- and does the output match the intended standard.

If not, reject and correct the spec or prompt.

---

## Stage 9 — Iterate only where needed

If Codex fails, do not blindly keep prompting.

Diagnose:

```text
Was the spec unclear?
Was the plan wrong?
Was the prompt too loose?
Was the validation test weak?
Was the template insufficient?
Was Codex allowed too much freedom?
```

Then fix the controlling file or prompt before rerunning.

---

## 9. Recommended Reading Order for Codex

A general reading order is:

```text
1. AGENTS.md
2. PROJECT_CONTEXT.md
3. SPEC.md
4. PLANS.md
5. REFERENCES.md if present
6. SKILL.md if present
7. README.md
8. configs/
9. existing source code
10. tests/
```

`AGENTS.md` should also state this order.

---

## 10. Recommended Codex Prompt Structure

A strong Codex prompt usually has this shape:

```text
Mission:
What Codex must do.

Read first:
Exact files to read in order.

Scope:
What is allowed and what is out of scope.

Implementation rules:
Architecture, style, file placement, constraints.

Validation:
Commands to run and checks to pass.

Stop conditions:
When Codex must stop and report instead of forcing progress.

Final report:
What Codex must summarize.
```

Example skeleton:

```text
Read AGENTS.md first, then PROJECT_CONTEXT.md, SPEC.md, and PLANS.md.

Mission:
Implement Milestone X only.

Scope:
Do not add unrelated features.
Do not change the public interface unless required.
Do not modify protected files.

Implementation:
Follow the architecture in SPEC.md.
Use the plan in PLANS.md.
Keep changes minimal and traceable.

Validation:
Run the tests listed in PLANS.md.
If tests fail, fix only issues related to this milestone.

Stop conditions:
Stop if required data/config is missing.
Stop if implementation would require changing project scope.

Final report:
List files changed, commands run, tests passed/failed, outputs generated, assumptions, limitations, and next step.
```

## 11. What to Put in `AGENTS.md`

A strong `AGENTS.md` should include:

```text
Required reading order
Project scope
Files/folders protected from edits
Allowed edit locations
Coding standards
Dependency rules
Data/privacy rules
Validation commands
Stop conditions
Final report format
```

Example stop conditions:

```text
Stop if required data is missing.
Stop if the task requires changing the approved scope.
Stop if tests cannot be run.
Stop if a command hangs beyond the allowed timeout.
Stop if implementation would require inventing labels, credentials, or external data.
```

---

## 12. What to Put in `PROJECT_CONTEXT.md`

A strong `PROJECT_CONTEXT.md` should include:

```text
Project title
Project background
Current project phase
Main objective
Inputs
Outputs
Approved methods
Rejected methods
Constraints
Known risks
Definition of done
```

This is where domain-specific methodology belongs.

---

## 13. What to Put in `SPEC.md`

A strong `SPEC.md` should include:

```text
Functional requirements
Non-functional requirements
Data/input requirements
Output requirements
Architecture requirements
Validation requirements
Error handling
Acceptance criteria
Out-of-scope items
```

`SPEC.md` should be precise enough that Codex can implement without guessing.

---

## 14. What to Put in `PLANS.md`

A strong `PLANS.md` should include:

```text
Milestones
Task checklist
Implementation order
Validation commands
Expected outputs
Progress log
Blockers
Completion criteria
```

For complex projects, require Codex to update the progress log after each milestone.

---

## 15. What to Put in `REFERENCES.md`

Use `REFERENCES.md` when adapting from previous projects.

It should include:

```text
Reference project/file list
What to learn from each reference
What not to copy
How the current project differs
Which files are read-only
```

This prevents blind copying.

---

## 16. What to Put in `SKILL.md`

Use `SKILL.md` when the workflow is reusable across projects.

It should include:

```text
Reusable method
Required steps
Common pitfalls
Validation rules
Output expectations
Stop conditions
```

Examples:

```text
healthcare ML skill
dashboard UI skill
data preprocessing skill
paper writing skill
deployment skill
```

---

## 17. Validation Rules

Every project should define validation before implementation.

Examples:

### Software app

```text
unit tests pass
app builds
key routes load
no console/runtime errors
```

### Data project

```text
data loads
schema validated
outputs generated
row counts reported
missing values checked
```

### ML project

```text
split is leakage-safe
preprocessing fit on train only
metrics generated
artifacts saved
reproducibility seed set
```

### Research/reporting project

```text
sections complete
claims supported
citations included
format requirements satisfied
```

## 18. Common Failure Modes

### 18.1 Vague prompts

Failure:

```text
Finish the project.
```

Fix:

```text
Implement Milestone 1 from PLANS.md only.
```

---

### 18.2 Weak spec

Failure:

```text
Codex guesses architecture or scope.
```

Fix:

```text
Update SPEC.md before coding.
```

---

### 18.3 No stop conditions

Failure:

```text
Codex forces progress by inventing missing details.
```

Fix:

```text
Tell Codex when to stop and report.
```

---

### 18.4 Superficial validation

Failure:

```text
Codex says done because code exists.
```

Fix:

```text
Require tests, commands, outputs, and explicit validation results.
```

---

### 18.5 Hidden implementation

Failure:

```text
Codex moves logic into unexpected files.
```

Fix:

```text
Specify exactly where implementation logic must live.
```

---

### 18.6 Over-engineering

Failure:

```text
Codex creates unnecessary modules, abstractions, or architecture.
```

Fix:

```text
Require minimal, scoped, spec-aligned changes.
```

---

### 18.7 Conflicting instructions

Failure:

```text
Multiple markdown files say different things.
```

Fix:

```text
Define instruction priority and remove duplicates.
```

---

## 19. Instruction Priority

When files conflict, use this priority:

```text
AGENTS.md
→ PROJECT_CONTEXT.md
→ SPEC.md
→ PLANS.md
→ REFERENCES.md
→ SKILL.md
→ README.md
```

For project-specific decisions, `PROJECT_CONTEXT.md` and `SPEC.md` should override generic reusable skills.

For behaviour and safety, `AGENTS.md` should override everything else.

---

## 20. Final Report Standard for Codex

Every Codex run should end with a report like:

```text
Files changed
Files created
Files deleted
Commands run
Tests passed/failed
Outputs generated
Validation results
Assumptions
Limitations
Blocked items
Next recommended step
```

For failed runs, Codex should report:

```text
where it failed
why it failed
what was attempted
what remains unchanged
recommended recovery step
```

---

## 21. Minimal Setup for a New Project

For a new project, start with:

```text
AGENTS.md
PROJECT_CONTEXT.md
SPEC.md
PLANS.md
README.md
```

Then add optional files only if needed:

```text
REFERENCES.md
SKILL.md
TASKS.md
```

Do not overcomplicate the repo with too many overlapping instruction files.

---

## 22. Strategic Takeaway

The best way to use ChatGPT + Codex is not one clever prompt.

The best way is to build a repo-level instruction system:

```text
AGENTS.md controls behaviour.
PROJECT_CONTEXT.md explains meaning.
SPEC.md defines success.
PLANS.md defines execution.
Tests prove completion.
Human review decides acceptance.
```

This turns Codex from a free-form code generator into a controlled implementation agent.

The goal is:

```text
less vibes
more contract
less guessing
more validation
less rework
more reproducibility
```
